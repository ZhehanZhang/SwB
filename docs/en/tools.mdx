`tools/list` shows the tools your sign-in permits. An unrestricted owner sign-in shows the tools from all enabled blocks.

## Paired keys

A paired key can use these tools within the access the owner grants it.

| Use | Tools and limits |
| - | - |
| Messages | Use `send` and `targets`. Use `agent_send` when legacy names are enabled. Use `inbox`, `wait`, `reply`, `status`, `result`, `cancel` and `get_message` within your key's conversation access |
| Memory and projects | Use `context_pack` and `project_list` within the access your key allows. Use the memory tools in granted scopes |
| Routes | Use `routes_list` and `routes_resolve`. For `routes_set` and `routes_remove`, set `agent` to your own agent name. Use a project within your key's scopes |
| Setup | Use `switchboard_status` and `modes_status` to check status. Use `connect` for client instructions. Use the owner's sign-in for block setup and to issue pairing codes |
| Blocks | Use block tools within your granted access and the actions that the channel mode allows |

The owner's unrestricted sign-in is required for `login_link`, `connect_code`, `connect_list`, `connect_revoke`, `visibility_list` and `visibility_set`. Use it for `project_create`, `project_update`, `project_sync` and `space_mode`. It also grants `memory_promote`, `routine_register`, `routine_add`, `routine_remove`, `discord_provision` and `telegram_provision`.

The owner can limit tools with `auth.key_tools` and send targets with `auth.key_targets`. The `auth.key_scopes` setting limits routing, messages and conversations. Memory tools use the grants SwB saves for each paired key.

## Messages

| Tool | Use |
| - | - |
| `send` | Put the work or message in `task`. Set `to` to choose a target. Leave `to` empty to use a route when the key allows it |
| `agent_send` | Deprecated tool. Pass the agent name in `to`, for example `to="codex"`. `blocks.mcp.legacy_aliases` enables it by default. For new calls, use `send` with `to="agent:codex"` |
| `wait` | Wait for new messages or replies |
| `inbox` | Read your inbox and return at once |
| `reply` | Pass the `handle` from a send or inbox item in `conversation`. Put the reply in `text` |
| `status` | Show the state of one conversation. For Capy, use `messages` for the number of recent messages. Set `include_tools=true` to include tool activity |
| `switchboard_status` | Show your sign-in identity, wait limits, blocks and instance health |
| `result` | Get the final reply of a conversation. Use `tail` to set the number of recent replies or messages where supported |
| `cancel` | Stop following a conversation |
| `targets` | List available target addresses. Your key and the target's rules control where you can send |
| `get_message` | Read a stored message with the `message_id` from your inbox or an MCP event |

### Inbox cursor

A cursor marks a position in the inbox. The `inbox` and `wait` tools save a new position when they return items. Filters can advance a separate position. A later `wait` reads from the saved position. Pass `since_cursor=0` to `inbox` to read from the start. Pass a returned `cursor` as `since_cursor` to continue from that position.

Scripts can call `GET /inbox/poll` with a bearer key to wait for items in their own inbox. Pass the returned `cursor` as `after` to resume. The default starts at the current end of the inbox. The call returns when items arrive or the wait time ends. It leaves the MCP cursor unchanged. Use the [inbox event stream](/docs/connect#inbox-event-stream) to receive messages as they arrive. Use `inbox` to read context items and Watch digests your sign-in can see.

For a paired key, a message or conversation outside its access gives the same error as a missing ID. See [Keys with limits](/docs/security#keys-with-limits).

### Send options

| Option | Use |
| - | - |
| `wait_s` | Set the time in seconds to wait for the first reply from a block. SwB applies the agent's wait limit. Use `wait` for agent mailboxes |
| `forward` | Pass the ID of an eligible conversation you received with `owner` trust. SwB sends the final reply to the original sender |
| `new_conversation` | Set `true` to start a new thread in the Capy Captain's project. Set `false` to send to the Capy Captain's thread |
| `files` | Attach files to a Capy task. Give each file a `name` and either `text` or `base64` content. Use `media_type` to set the file type |
| `repos` | Pass the repositories for a Capy task as `owner/repo` names. Use repositories linked to the SwB project |
| `in_reply_to` | To answer a message, use `reply` with `conversation` in place of this option |

## Memory and projects

Use the owner's sign-in or a credential with a grant for the memory scope. To update, move or delete an entry as an agent, use the credential that last wrote it. The owner can manage any entry. Changes to an existing entry in `general` require owner access.

| Tool | Use |
| - | - |
| `context_pack` | Read a project briefing. It includes `general` only when the credential grants access. The Capy section for a paired key shows its agent's work within its conversation scopes |
| `memory_write` | Save in a granted scope. Pass `scope`, `namespace`, `title` and `body`. A namespace groups entries within a scope. Use up to three lowercase levels, such as `notes/meetings`. For project memory, pass the same project in `project` and `scope`. To write to `general`, ask the owner to confirm. Then set `confirm_general=true` |
| `memory_search` | Search with `query`. Pass `project` for that project and any granted `general` memory. Set `include_general=false` for that project alone. Use `scopes` for exact grants such as `agent:<name>` |
| `memory_list` | List entries with the same scope inputs as `memory_search` |
| `memory_read` | Read one entry with its history in a granted scope |
| `memory_delete` | Remove an entry in a granted scope |
| `memory_move` | Move an entry to a project or agent scope. You need grants for both scopes |
| `memory_promote` | Move an entry to `general`. Use the owner's sign-in |
| `memory_summary` | Load a short index of granted memory at the start of a session |
| `memory_view` | Show a folder or a file under `/memories`. See [Memory](/docs/memory) |
| `memory_create` | Make a file in a topic folder |
| `memory_str_replace` | Change one exact passage in a file |
| `memory_insert` | Add text after a line |
| `memory_rename` | Move a file or topic folder to a new path |
| `memory_history` | Show each change to an entry |
| `memory_restore` | Put back an earlier version of an entry |
| `memory_sync` | Copy memories from the agent's own memory into SwB |
| `memory_settings` | Turn memory sync on or off. Use the owner's sign-in |
| `memory_export` | Download all memory as a zip file. Use the owner's sign-in |
| `memory_import` | Load memory from a zip file. Use the owner's sign-in |
| `memory_backup_configure` | Set the Git backup repository. Use the owner's sign-in |
| `memory_backup_status` | Show the Git backup status. Use the owner's sign-in |
| `memory_backup_now` | Start a Git backup now. Use the owner's sign-in |
| `memory_backup_restore` | Load memory from the Git backup. Use the owner's sign-in |
| `project_list` | List projects and their links |
| `project_create` | Make a project |
| `project_update` | Rename, link, archive or make a project private |
| `project_sync` | Link projects to their matches again |

Use `links` in `project_update` to set these values. SwB offers the project link keys for the configured agents and blocks.

| Key | Value |
| - | - |
| `repos` | List of repository names in `owner/repo` form |
| `claude_project` | Claude project name or ID |
| `chatgpt_project` | ChatGPT project name or ID |
| `capy_project` | Capy project name or ID |

A private project requires a grant that names that project or owner access. For `memory_search` and `memory_list`, specify the private project in `project`. Use `scopes` for any additional public projects you have access to.

## Routes

A route picks a target for `send`. Use a block that accepts routes, such as `capy`, `claude-routine` or `grok-routine`. Use `to="agent:<name>"` to reach an agent's mailbox directly. Use `to="agent:muse"` to send to the Muse mailbox. Use `to="muse:gadget:muse"` to [wake Muse](/docs/setup/muse#wake-muse-in-real-time).

| Tool | Use |
| - | - |
| `routes_list` | List all routes, mailbox routes included |
| `routes_set` | Save a route. Give `target` an agent mailbox, such as `agent:<name>`, or a block address, such as `capy:captain:<name>`. Use `agent` or `project` to limit the route |
| `routes_resolve` | Show the matching route for one destination. Pass `block`, such as `grok-routine` or `agent` |
| `routes_remove` | Remove the route for the exact `agent` and `project` on the chosen `block` |

Use `block` to check or remove a route for one destination. By default, `routes_resolve` checks the agent and project together, then the project, then the agent, then the global route. At each level, it checks blocks in order and then checks `agent`. By default, `routes_remove` checks that same destination order for the exact agent and project.

### GitHub

| Tool | Use |
| - | - |

### [Webhooks](/docs/blocks/webhooks)

| Tool | Use |
| - | - |
| `webhook_create` | Create a named inbound or outbound webhook |
| `webhook_list` | List webhooks with their addresses, counts and secret status |
| `webhook_rotate` | Get a claim link for a new secret and set an optional grace period |
| `webhook_revoke` | Stop a webhook and delete its saved secrets |
| `webhook_test` | Send a sample inbound event or outbound message |

For outbound webhooks, `webhook_create` and `webhook_rotate` accept `allow_private` and `senders`. Set `allow_private` to `true` for private HTTPS receivers or ports other than 443. List connected agents in `senders` to let them send. By default, only the owner can send. Omit both fields in `webhook_rotate` to keep their current values.
