Cloudflare Tunnel donne à SwB une adresse HTTPS publique. Un **tunnel** connecte votre serveur à Cloudflare. Cloudflare propose les tunnels dans son offre gratuite.

Suivez [Docker Compose](/fr/docs/deploy#docker-compose) pour démarrer SwB.

<span id="tunnel-rapide" />

## Tunnel rapide [#quick-tunnel]

Utilisez un tunnel rapide pour obtenir une adresse temporaire. Installez [cloudflared](https://developers.cloudflare.com/tunnel/downloads/) sur le serveur SwB. Ce programme connecte SwB à Cloudflare. Exécutez cette commande sur le serveur.

```sh
cloudflared tunnel --url http://localhost:8870
```

Dans `.env`, définissez `SWB_PUBLIC_URL` sur l'adresse HTTPS affichée dans le terminal. Si votre configuration contient `public_url`, mettez-le à jour avec la même valeur. Ajoutez le connecteur aux [proxys de confiance](#trusted-proxies). Exécutez `docker compose up -d` pour appliquer les paramètres.

L'adresse change à chaque démarrage du tunnel. Les connexions OAuth et les clés d'accès utilisent cette adresse. Pour une adresse fixe, utilisez un tunnel nommé.

<span id="tunnel-nommé" />

## Tunnel nommé [#named-tunnel]

Utilisez un tunnel nommé pour obtenir une adresse fixe sur votre domaine.

### Avant de commencer

Utilisez un compte Cloudflare autorisé à gérer les tunnels et les applications Access de votre domaine. Autorisez votre serveur à se connecter à Cloudflare sur le port 7844.

### Créer le tunnel

Suivez le guide [Create a tunnel](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/get-started/create-remote-tunnel/). Copiez le jeton du tunnel depuis la commande d'installation. Gardez le jeton privé.

Pour exécuter le connecteur avec Compose, placez le jeton dans `.env` sous le nom `TUNNEL_TOKEN`. Démarrez le connecteur.

```sh
docker compose --profile tunnel up -d
```

Pour exécuter le connecteur directement sur l'hôte, exécutez la commande d'installation que Cloudflare fournit pour votre système.

Quand le connecteur apparaît dans Cloudflare, sélectionnez **Continue**.

### Protéger la console [#cloudflare-access]

Cloudflare Access réserve la console SwB à votre compte. [Créez une application Access](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/self-hosted-public-app/) pour le nom d'hôte de SwB. Définissez l'action de la stratégie sur **Allow**. Sélectionnez **Emails** sous **Include**. Saisissez votre adresse e-mail.

Créez une deuxième application Access sur le même nom d'hôte pour les chemins marqués **Bypass**. Définissez l'action de sa stratégie sur **Bypass**. Sous **Include**, sélectionnez **Everyone**.

| Chemin | Stratégie Access |
| --- | --- |
| `/mcp`, `/register`, `/token`, `/revoke`, `/.well-known/*` | Bypass |
| `/healthz`, `/connect`, `/avatars/*` | Bypass |
| `/inbox/poll`, `/inbox/events` | Bypass |
| `/companion/*` | Bypass |
| `/github/webhook` | Bypass pour GitHub |
| `/hooks/*` | Bypass pour Webhooks et le hook Muse |
| Tous les autres chemins, dont `/pairing/companion`, `/authorize` et `/inbox` | Propriétaire |

SwB vérifie les codes d'appairage sur `/companion/pair`. Il vérifie la clé de l'appareil sur les autres requêtes du compagnon. Si vous utilisez Access, demandez à un agent doté de l'accès propriétaire d'appeler `companion_code`.

### Autoriser les requêtes HTTP des agents

La fonction Browser Integrity Check peut bloquer les requêtes des agents. Ajoutez une [Configuration Rule](https://developers.cloudflare.com/rules/configuration-rules/) dans votre zone Cloudflare pour ces chemins SwB.

Remplacez `swb.example.com` par le nom d'hôte de votre SwB. Utilisez cette expression de règle.

```text
(http.host eq "swb.example.com" and (
  starts_with(http.request.uri.path, "/mcp") or
  starts_with(http.request.uri.path, "/hooks/") or
  starts_with(http.request.uri.path, "/.well-known/") or
  http.request.uri.path in {"/register" "/token" "/revoke" "/connect"} or
  starts_with(http.request.uri.path, "/inbox/") or
  starts_with(http.request.uri.path, "/companion/")
))
```

Dans la règle, définissez `Browser Integrity Check: Off`. SwB continue d'appliquer ses propres règles d'accès.

### Définir l'adresse SwB

Dans `.env`, définissez `SWB_PUBLIC_URL` sur votre adresse publique.

```dotenv
SWB_PUBLIC_URL=https://swb.example.com
```

Si votre configuration contient `public_url`, mettez-le à jour avec la même valeur.

Ajoutez à `config/switchboard.yaml` le domaine de votre équipe et la balise d'audience de l'application propriétaire. Cette balise indique à SwB l'application qui a émis le jeton.

| Valeur | Où la trouver | Clé de configuration |
| --- | --- | --- |
| Domaine de l'équipe | **Zero Trust** → **Settings** | `auth.cloudflare_access.team_domain` |
| Application Audience (AUD) Tag | Application propriétaire → **Additional settings** | `auth.cloudflare_access.aud` |
| Votre adresse e-mail | Stratégie propriétaire → **Emails** | `auth.owner_emails` |

```yaml
auth:
  owner_emails: [owner@swb.example.com]
  cloudflare_access:
    team_domain: example.cloudflareaccess.com
    aud: "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"
```

SwB lit d'abord le jeton dans l'en-tête `Cf-Access-Jwt-Assertion`. Il utilise le cookie `CF_Authorization` comme seconde source. Un cookie est une valeur que le navigateur envoie avec une requête. SwB vérifie la signature RS256 avec les clés publiques de `team_domain`. L'émetteur du jeton doit correspondre à l'adresse HTTPS de `team_domain`. Le jeton doit indiquer `aud` comme audience. SwB vérifie les dates d'émission, de début de validité et d'expiration quand le jeton les fournit. SwB compare l'adresse e-mail en minuscules avec `owner_emails`.

<span id="proxys-de-confiance" />

### Proxys de confiance [#trusted-proxies]

Un proxy inverse transmet les requêtes à SwB. Ajoutez son adresse ou son réseau dédié à `trusted_proxies` dans `config/switchboard.yaml`. Écrivez les plages réseau au format CIDR, par exemple `192.0.2.0/24`.

Vous pouvez aussi définir `SWB_TRUSTED_PROXIES` dans `.env`. Séparez les entrées par des virgules. Le paramètre YAML a la priorité.

Pour un Cloudflare Tunnel, ajoutez l'adresse du connecteur ou son réseau dédié. Pour une connexion de bouclage IPv4, utilisez `127.0.0.1/32`. Utilisez l'entrée `cloudflare` pour les connexions directes depuis les serveurs en périphérie de Cloudflare.

Exécutez `docker compose --profile tunnel up -d` pour appliquer les paramètres avec le connecteur Compose. Pour un connecteur sur l'hôte, exécutez `docker compose up -d`.

### Publier le nom d'hôte

Ouvrez l'onglet **Routes** du tunnel. Sélectionnez **Add route**. Choisissez **Published application**. Saisissez votre nom d'hôte public.

Pour le connecteur Compose, définissez **Service URL** sur `http://switchboard:8000`. Pour un connecteur sur l'hôte, utilisez `http://localhost:8870`. Sélectionnez **Add route** pour enregistrer la route.

### Vérifier la connexion

Ouvrez votre adresse publique dans un navigateur. Connectez-vous à Cloudflare Access. [Vérifiez l'adresse publique](https://swb.example.com/healthz) pour vérifier que SwB répond.

Ouvrez `https://swb.example.com/mcp` dans une fenêtre de navigation privée. SwB renvoie `401` avec un en-tête `WWW-Authenticate`. Si Cloudflare affiche sa page de connexion, vérifiez la stratégie Bypass.

## Configurer une application

Une fois le nom d'hôte opérationnel, suivez [Connecter vos agents](/fr/docs/connect) pour configurer une application. Utilisez l'adresse MCP publique, par exemple `https://swb.example.com/mcp`. Demandez à votre agent d'appeler `switchboard_status` pour vérifier son identité SwB.
