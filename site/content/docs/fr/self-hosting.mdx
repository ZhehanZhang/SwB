## Docker Compose

Installez Docker Compose 2.24 ou une version ultérieure. Exécutez ces commandes avec un utilisateur ordinaire, propriétaire du dossier de données.

```bash
git clone --branch release/1.0 https://github.com/ZhehanZhang/SwB.git
cd SwB
(umask 077; cp .env.example .env)
{
  printf 'SWB_UID=%s\n' "$(id -u)"
  printf 'SWB_KEY_OWNER='
  openssl rand -hex 32
} >> .env
printf 'SWB_PUBLIC_URL=http://localhost:8870\n' >> .env
mkdir -p data
docker compose up -d --build --wait
curl -fsS http://127.0.0.1:8870/healthz
docker compose exec -T switchboard swb login-link --url http://127.0.0.1:8000
```

Dans les cinq minutes, ouvrez le lien de connexion à usage unique affiché dans le terminal. Gardez ce lien privé.

Le navigateur utilise `http://localhost:8870` pour la connexion du propriétaire. La commande dans le conteneur utilise le port `8000`. Compose garde les données dans `./data`. Après une modification de `.env`, exécutez de nouveau `docker compose up -d`.

Pour un serveur distant, redirigez son port `8870` vers le port local `8870` avant d'ouvrir le lien.

Une requête anonyme vers `/healthz` renvoie `status` et `version`. Utilisez une session propriétaire ou la clé propriétaire pour obtenir l'état de santé détaillé.

## <ProviderMark name="cloudflare" /> Cloudflare Tunnel [#cloudflare-tunnel]

Un Cloudflare Tunnel donne à SwB une adresse HTTPS publique. Cloudflare propose les tunnels dans son offre gratuite.

### Tunnel rapide

Utilisez un tunnel rapide pour essayer SwB à une adresse temporaire. Exécutez cette commande sur l'hôte avec `cloudflared`, le programme qui connecte SwB à Cloudflare.

```bash
cloudflared tunnel --url http://localhost:8870
```

Définissez `SWB_PUBLIC_URL` sur l'adresse HTTPS affichée dans le terminal. Si votre configuration contient `public_url`, mettez aussi ce paramètre à jour. Redémarrez SwB. L'adresse change à chaque démarrage du tunnel. Les connexions OAuth et les clés d'accès utilisent cette adresse. Pour une adresse durable, utilisez un tunnel nommé.

### Tunnel nommé

Utilisez un compte Cloudflare gratuit avec votre domaine. Suivez le [guide de configuration de Cloudflare](/fr/docs/setup/cloudflare) pour créer le tunnel et configurer Access. Définissez `SWB_PUBLIC_URL` sur votre adresse publique, par exemple `https://swb.example.com`. Si votre configuration contient `public_url`, mettez-y aussi l'adresse à jour.

Pour un tunnel sur l'hôte SwB, faites pointer son adresse de service vers `http://localhost:8870`. Définissez `SWB_TRUSTED_PROXIES` sur l'adresse du connecteur, par exemple `127.0.0.1/32` pour une connexion en boucle locale IPv4.

Pour le tunnel Compose, faites pointer son adresse de service vers `http://switchboard:8000`. Placez le jeton du tunnel dans `.env` sous le nom `TUNNEL_TOKEN`. Ajoutez l'adresse du connecteur ou son réseau dédié à `trusted_proxies`. Démarrez Compose avec le profil tunnel.

```bash
docker compose --profile tunnel up -d
```

## Proxys de confiance

Un proxy inverse transmet les requêtes à SwB. Ajoutez l'adresse du proxy ou son réseau dédié à `trusted_proxies` dans `config/switchboard.yaml`. Écrivez les plages réseau au format CIDR, par exemple `192.0.2.0/24`.

Vous pouvez aussi définir `SWB_TRUSTED_PROXIES` dans `.env`. Séparez les entrées par des virgules. Le paramètre YAML a la priorité.

Pour un Cloudflare Tunnel sur l'hôte SwB ou sur le réseau Docker, ajoutez l'adresse du connecteur du tunnel ou son réseau dédié. Le connecteur se connecte directement à SwB. Utilisez l'entrée `cloudflare` pour les connexions directes depuis les serveurs en périphérie de Cloudflare.

## Cloudflare Access

Suivez le [guide de configuration de Cloudflare](/fr/docs/setup/cloudflare). Il explique comment configurer SwB et définir les règles d'accès du propriétaire et des requêtes des clients.

## Plateformes d'hébergement

Utilisez une seule instance SwB avec un disque persistant monté sur `/data`. Consultez le [guide de déploiement](https://github.com/ZhehanZhang/SwB/tree/release/1.0/deploy) pour les modèles Railway, Render et Fly.io et pour le script Koyeb.

## Railway [#railway]

Déployez depuis le [modèle SwB sur Railway](https://railway.com/deploy/swb). Gardez une seule réplique. Le modèle monte un volume sur `/data`.

Pour un SwB toujours actif, choisissez l'offre Hobby. Elle coûte 5 $ par mois et inclut 5 $ d'utilisation.

L'[offre gratuite](https://docs.railway.com/reference/pricing/free-trial) inclut 1 $ d'utilisation par mois. Ce montant couvre environ 100 Mo de RAM en continu. Une instance SwB de test utilisait environ 107 Mio au repos. Les services de l'offre gratuite s'arrêtent quand le dollar est épuisé.

## Fly.io [#fly]

Utilisez le clone de la version SwB créé dans l'[exemple Docker Compose](#docker-compose). Installez l'[outil en ligne de commande Fly.io](https://docs.fly.io/flyctl/). Connectez-vous à Fly.io.

Exécutez `sh deploy/fly.sh my-swb` depuis le dossier SwB. Remplacez `my-swb` par un nom d'application unique. Le script utilise `fly deploy --ha=false` pour démarrer une seule Machine.

Ouvrez la page de connexion de votre application. Copiez `SWB_SETUP_CODE` depuis le fichier `.env.swb-setup-fly-my-swb` de votre clone. Saisissez-le dans **Setup code**. Supprimez le fichier après la connexion.

Consultez le [forfait gratuit de Fly.io](https://docs.fly.io/about/free-plan) et les [tarifs actuels](https://fly.io/docs/about/pricing/) pour la facturation.

## Sauvegardes et mises à jour

Arrêtez SwB avant de copier son dossier de données. Conservez le dossier complet, avec la base de données et ses clés, dont `mcp-events.key` et `claim-key`. Sauvegardez aussi vos fichiers de configuration et `.env`. Gardez la sauvegarde privée. Installez ou compilez la nouvelle version. Démarrez SwB avec le même dossier de données.

## Exporter la mémoire

Exécutez l'export dans le conteneur Compose.

```bash
docker compose exec -T switchboard swb export /data/export
```

L'export enregistre des fichiers Markdown classés par portée dans `./data/export` sur l'hôte. Il comprend un fichier `INDEX.md`. Définissez `memory.mirror_dir` pour garder une copie Markdown à jour.
