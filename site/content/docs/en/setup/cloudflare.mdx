---
title: Cloudflare
description: Give SwB a public HTTPS address with Cloudflare Tunnel and protect it with Cloudflare Access.
---

Cloudflare Tunnel gives SwB a stable public HTTPS address. A tunnel is a connection from your server to Cloudflare, so the server keeps its ports closed. Cloudflare Access lets only you open the SwB console.

## Before you start

You need a Cloudflare account, a domain in that account and a Zero Trust organization. The Zero Trust Free plan is enough, and Cloudflare asks for payment details. You need the right to manage tunnels, Access applications and DNS for the SwB hostname.

SwB must run on a server that can reach Cloudflare on port 7844. The Compose setup of SwB listens on `http://switchboard:8000`.

## Your steps

<Steps>
<Step>
### Create the tunnel

Click **Networking** → **Tunnels** → **Create a tunnel** in the Cloudflare dashboard.
</Step>
<Step>
### Name the tunnel

Type a name for the tunnel. Click **Create Tunnel**.
</Step>
<Step>
### Store the tunnel token

Copy the tunnel token from the install command. Put it in the `.env` file of SwB as `TUNNEL_TOKEN`.
</Step>
<Step>
### Start the connector

Run `docker compose --profile tunnel up -d` on the SwB server. Click **Continue** when the connector shows in the dashboard.
</Step>
<Step>
### Make the owner policy

Click **Zero Trust** → **Access controls** → **Policies** → **Add a policy**. Set **Action** to **Allow**.
</Step>
<Step>
### Add your email

Under **Include** → **Emails**, type your email address. Click **Save**.
</Step>
<Step>
### Protect the console

Click **Access controls** → **Applications** → **Create new application** → **Self-hosted and private**. Add your SwB hostname with the owner policy.
</Step>
<Step>
### Make the bypass policy

Add a second policy with **Action** set to **Bypass** and **Include** set to **Everyone**. Click **Save**.
</Step>
<Step>
### Open the machine paths

Create a second application on the same hostname with the paths in the table below and the bypass policy. Click **Create**.
</Step>
<Step>
### Copy the Access values

Copy the **Application Audience (AUD) Tag** from the owner application → **Additional settings**. Copy your team domain from **Zero Trust** → **Settings**.
</Step>
<Step>
### Set the SwB values

Put the values below in the `.env` file of SwB. Restart SwB.
</Step>
<Step>
### Publish the hostname

Click **Networking** → **Tunnels** → your tunnel → **Routes** → **Add route** → **Published application**. Type the hostname and set **Service URL** to `http://switchboard:8000`.
</Step>
<Step>
### Add the route

Click **Add route**.
</Step>

<Step>
### Sign in

Open https://swb.example.com in a new browser window. Sign in with your identity provider.
</Step>

| Path | Policy |
| --- | --- |
| `/mcp`, `/register`, `/token`, `/revoke`, `/healthz`, `/connect` | Bypass |
| `/.well-known/*`, `/inbox`, `/inbox/*`, `/avatars/*` | Bypass |
| `/github/webhook` | Bypass, for GitHub only |
| All other paths, with `/` and `/authorize` | Owner |

```sh
SWITCHBOARD_PUBLIC_URL=https://swb.example.com
SWITCHBOARD_OWNER_EMAILS=owner@example.com
CLOUDFLARE_ACCESS_TEAM_DOMAIN=example.cloudflareaccess.com
CLOUDFLARE_ACCESS_AUD=<application audience tag>
```

SwB checks the Access sign-in of each owner request. The bypass paths use the sign-in of SwB itself.

## What the agent does

An agent with the Cloudflare connector can make the tunnel, the Access policies and the applications through the Cloudflare API. It makes its own API token with the least access for your account and zone. You keep your own Cloudflare tokens to yourself.

After the address works, the agent calls `connect` for your app, for example `what="claude"` or `what="chatgpt"`. SwB returns the MCP address `https://swb.example.com/mcp`. `switchboard_status` shows which SwB identity the app uses.

## Credentials

| Token | Where Cloudflare shows it | Format | Where it goes |
| --- | --- | --- | --- |
| Tunnel token | **Networking** → **Tunnels** → your tunnel, in the install command | Long text that starts with `eyJ` | `TUNNEL_TOKEN` in the `.env` file of SwB |
| Application audience tag | Owner application → **Additional settings** | Long hex text | `CLOUDFLARE_ACCESS_AUD` in the `.env` file |
| Team domain | **Zero Trust** → **Settings** | `<team>.cloudflareaccess.com` | `CLOUDFLARE_ACCESS_TEAM_DOMAIN` in the `.env` file |

The tunnel token gives control of the tunnel. Keep it in the `.env` file only.

## Check the connection

Check that the tunnel shows **Healthy** under **Networking** → **Tunnels**. Open `https://swb.example.com/healthz` and check that SwB answers.

Send a request to `https://swb.example.com/mcp` before you sign in. SwB answers with `401` and a `WWW-Authenticate` header. A Cloudflare sign-in page in its place means that the bypass application is missing.

## Fix problems

OAuth needs all the machine paths. OAuth is the sign-in flow that apps use to connect to SwB. If one path is missing, the app stops at sign-in.

The path `/inbox/*` leaves out `/inbox` itself. Add both paths.

Keep `/` and `/authorize` under the owner policy. A bypass on these paths opens the console to everyone.
