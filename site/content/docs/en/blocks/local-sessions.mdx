---
title: Local sessions
description: Send messages to coding agents that run on a paired device.
---

A local session is an open workspace for a coding agent on a paired device. SwB lists it as a target. A target is an address that can receive a message.

## Pair the device

Follow [Pair a device](/docs/companion#pair-a-device) with the command for your agent below. Use one `--cap` option for each feature. To change the features on a paired device, [disconnect it](/docs/companion#disconnect) first.

From an owner agent, call `targets(block="local")` to check each setup. Copy the address of your session. The format is `local:session:<harness>:<id>`. A harness is the program that runs the agent.

## Send a message

Call `send` with the session address in `to`. SwB puts the message in the agent's mailbox. For a direct connection, SwB also tries to deliver the message into the open session. Read the answer with `result` in the same conversation.

| Status | Meaning |
| --- | --- |
| `working` | The agent is working |
| `blocked` | The agent is waiting for approval or input |
| `idle` | The agent is ready for work |
| `done` | The agent completed its work |
| `unknown` | The status is still to be confirmed |

For a blocked session, respond to the request in the session. SwB keeps the message in the mailbox.

SwB reports the session status to your deployment. It can also report the session name and folder name. SwB can send back one answer to a message it delivered. The rest of the session stays on the device.

## Status hooks

A hook runs a command when an agent reports a change. Status hooks work on macOS and Linux.

```sh
swb companion connect https://swb.example.com --cap hooks
```

Install the `swb` command with [pipx](/docs/install). Make it available on the agent's command search path. If you set `SWB_COMPANION_HOME`, use the same folder for the agent and the companion.

| Agent | Event command | Configuration |
| --- | --- | --- |
| Claude Code | `swb hook claude-code` | Merge the `hooks` from `channel/hooks/hooks.json` into `~/.claude/settings.json` |
| Gemini CLI | `swb hook gemini` | Install the SwB extension from the checkout as shown below |
| Codex | `swb hook codex` | Merge the `hooks` from `integrations/codex/hooks.json` into `~/.codex/hooks.json` |

Use the files from the [SwB release checkout](/docs/self-hosting#docker-compose). The SwB Claude Code plugin also includes these hooks. If you set `CODEX_HOME`, use its `hooks.json` for Codex.

```sh
gemini extensions install /path/to/SwB/integrations/gemini
```

Open a new session after you set up the hook. Check for its address in `targets(block="local")`. With the hooks capability by itself, sessions receive messages through their mailboxes.

## Herdr

Open a coding agent in a Herdr pane, an area in the terminal. The companion gets session events through Herdr's socket. A socket is a connection that programs use on the same device.

Set `HERDR_SESSION` if you use a named Herdr session. For a custom socket path, set `HERDR_SOCKET_PATH` in the companion's terminal.

```sh
swb companion connect https://swb.example.com --cap herdr --cap hooks
```

For replies from the pane, set up the applicable [status hook](#status-hooks). Check for a `local:session:herdr:<id>` target. Send a short test message to the target. Check that it appears in the pane. If you set up a status hook, check the reply with `result`.

## Codex

The Codex app server is a process that gives other programs access to open Codex sessions. Start it in one terminal.

```sh
codex app-server --listen unix://
```

Open a session from a second terminal.

```sh
codex --remote unix://
```

Use a separate terminal for the companion. Use the same `CODEX_HOME` there if you set it for the app server. For a custom socket path, set `SWB_CODEX_SOCKET`.

```sh
swb companion connect https://swb.example.com --cap codex
```

The companion reads session events from the app server. Check for a `local:session:codex:<id>` target. Send a short test message to the target. Check the reply with `result`.

## OpenCode

Start the OpenCode server on the device.

```sh
opencode serve --hostname 127.0.0.1 --port 4096
```

Open a session on that server. Set `SWB_OPENCODE_URL` to the server's local address. If the server uses a password, set `OPENCODE_SERVER_PASSWORD` in the companion's terminal.

```sh
SWB_OPENCODE_URL=http://127.0.0.1:4096 swb companion connect https://swb.example.com --cap opencode
```

The companion reads session events from the OpenCode server. Check for a `local:session:opencode:<id>` target. Send a short test message to the target. Check the reply with `result`.

## DeepSeek Harness

Use DeepSeek Harness `0.2.2-rc.5`. A profile is a set of app settings. Install the SwB bridge in the `web` profile. The bridge sends session events to the companion.

Use the local checkout for this release. The bridge is in the `release/1.0` branch. Replace `/path/to/SwB` with the absolute path to your checkout.

```sh
dsh plugin --profile web add /path/to/SwB/integrations/dsh
```

Restart DeepSeek Harness with the `web` profile. Open a session. If you set `SWB_COMPANION_HOME`, use the same absolute path for DeepSeek Harness and the companion.

```sh
swb companion connect https://swb.example.com --cap dsh
```

Check for a `local:session:dsh:<id>` target. Send a short test message to the target. Check the reply with `result`.
